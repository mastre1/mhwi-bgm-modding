# 实战 01：煌黑龙 ←「雨爱」（2026-10-25，14_00，游戏内验证成功）

> 本案价值 = 完整的反面教材史：v1~v6 六次失败各自堵死一条"看似合理"的旁路，v7 才确立标准链路。
> 全部结论已提炼进 SKILL.md §2/§5，本文保留排查逻辑供疑难时回溯。

## 背景

目标：`bgm_slugger_ingame_14_00.npck`（煌黑龙战斗 BGM，11 槽全 4ch/48kHz），音源《杨丞琳-雨爱》mp3。
当时手上的参照是一个第三方"示例 mod"，走了弯路。

## 失败史（每版堵死一条路）

| 版本 | 做法 | 结果 | 根因 |
|---|---|---|---|
| v1 | 第三方工具链：2ch 音源塞 4ch 槽（参照包本身是 2ch 删减版） | **静音** | **声道数不匹配**（游戏整段静音的表现形式） |
| v2 | 换原版 npck 做模板、自写 wem（oggenc2 aoTuV 编码 + 自写 AKPK 打包器） | 无声 | 第三方编码产物 setup 结构与 MHW 解码器预期不符 |
| v3 | 逐字段对齐原版 wem：codebook id 0x5BC4CA94、subtype 0x603104、alloc 21480/21976、逐包 seek 表、去 hash 块 | **乱码电子音** | "字段全对齐"也救不了——问题在编码器本身，不在字段 |
| v5 | 换 Wwise 2026.1.3 官方编码器编码后，**仍手改 uid/alloc 对齐原版值**再打包 | 乱码 | 官方编码是对的，**改字段又把它改坏了** |
| v6 | "零结构改动"：npck 大小/条目表/偏移与原版逐字节相同，数据原位填充 | 乱码 | **布局理论被排除**——问题从头到尾都是"谁编码的" |
| **v7** | **Wwise 2025.1.12 High 编码 + wwiseutil 1.1 `-replace` 标准重建，字段一个不动** | **成功** ✓ | — |

## 期间做过的实证（有保留价值）

- **码本库逐字节确认**：引擎内置码本库与 ww2ogg 的 `packed_codebooks_aoTuV_603.bin` 完全相同
  （MonsterHunterWorld.exe 偏移 62098760 起，598 本书全部命中）——所以"能被 603 库反解"
  不是兼容性判据，v3 产物反解出来就是正常音乐。
- **无损对照**：原版 wem 经 603 库反解 = 正常音乐；自建 wem 往返 corr=1.0 也无损——
  说明"数据可解码"与"游戏肯解"是两回事，缺口在编码器身份。
- **Wwise 版本不敏感**：2025.1.12.9287 与 2026.1.3 编码产物逐字节同构（uid 0x081E7C2F）。
- 2ch 数据进 4ch 槽 = 无声；同数据同结构仅编码器不同 = 乱码——两种失败形态不同，可据此分辨根因。

## v7 成功做法（即 SKILL.md §2 的直接来源）

1. 从游戏 chunk 定向提取原版 14_00（11 槽，A1 确认全 4ch/48kHz）；
2. mp3 → 48kHz wav → `pan=quad` 四声道（FL FR BL BR = L R L R）；
3. WwiseConsole create-new-project + `list.wsources`（Vorbis Quality High）+ convert-external-source；
4. wem 复制成 `1.wem..11.wem` → `wwiseutil -replace -f 原版.npck -t 槽目录 -o 成品.npck`；
5. verify_npck ALL OK + ww2ogg/revorb 回读 + 逐槽声道复核；
6. zip 根 `nativePC/sound/wwise/Windows/` 交付，盒子导入后启用。

## 排查方法论（当时真正起作用的）

- **每版只改一个变量**（编码器→字段→布局），失败结果能精确归因；
- 先造"能区分假设的测量"（逐字节同构检测、码本逐字节比对、往返无损验证）再动手改；
- 对照当时工具箱《使用说明.txt》的标准流程时发现：直觉上"不够高级"的 wwiseutil 替换链路
  才是对的——**工具箱文档的流程本身就是被验证过的答案，先照做，别发明**。
